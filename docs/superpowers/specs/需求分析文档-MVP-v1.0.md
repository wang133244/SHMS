## 1. 项目背景

### 1.1 业务背景

幼儿园现有业务细则以 Excel 表格保存，内容覆盖业务人员、后勤、保安、保健、保育和厨房等岗位，并按每日、每周、每月、学期等周期安排工作。当前需要一个微信小程序，让园内员工能够查看和提交任务，让管理员能够维护人员、审核任务模板和管理岗位职责知识。

本项目第一阶段只建设单个幼儿园内部的人员与岗位职责管理 MVP。部署方式、集团多园区、家长和幼儿业务暂不纳入本需求。

### 1.2 问题陈述

1. Excel 细则中的岗位、周期、时间和工作要求难以直接转化为每天可执行的任务。
2. 员工无法在一个入口查看本人今日任务、提交记录和岗位工作要求。
3. 管理员缺少任务逾期、修改申请和资料发布的统一追踪方式。
4. 直接让大模型生成任务或回答存在编造、越权检索和无法追溯的问题。
5. 不同岗位职责不同，必须根据登录身份做服务端鉴权和知识过滤。

### 1.3 项目目标

1. 用微信原生小程序提供员工端和管理员端入口。
2. 用 FastAPI 提供认证、人员、任务、园历、导入和对话 API。
3. 用 PostgreSQL + pgvector 保存业务关系数据、审计日志和岗位知识向量。
4. 用 LangGraph 编排严格的岗位 RAG 对话，只回答已发布且有来源的细则内容。
5. 用确定性任务规则生成应办任务，禁止 AI 创建、修改、分配或关闭任务。
6. 对员工提交、修改申请、管理员审核和历史版本进行完整追溯。

## 2. 用户分析

### 2.1 目标用户

| 用户角色 | 描述 | 核心需求 |
|----------|------|----------|
| 管理员 | 负责园内人员、岗位、任务模板、园历和知识库维护的用户 | 绑定员工、审核 Excel 草稿、发布模板和知识、查看任务及审核修改申请 |
| 普通员工 | 六类岗位中的在岗员工，每个岗位当前配置一人 | 查看本人任务、提交任务、申请修改、查询本岗位职责 |

岗位分类固定为：后勤、保安、保健、保育、厨房、业务人员。首版一名员工只属于一个岗位，不支持兼岗。

### 2.2 用户画像

- 管理员：熟悉园务工作但不一定熟悉技术，需要批量、可追溯、可审核的管理界面。
- 普通员工：以手机为主要设备，使用场景碎片化，需要快速查看今日待办、提交文字和现场照片。
- 保安岗位：当前只有一人，所有已启用保安任务直接分配给该员工；未来人员增加后再启用轮班。

### 3.2 详细功能描述

#### 3.2.1 微信登录与岗位绑定

**功能描述**：

员工使用微信小程序登录并授权手机号。后端根据管理员预置的员工手机号匹配唯一员工档案和岗位，成功后绑定微信 OpenID。

**用户故事**：

- 作为普通员工，我希望使用微信登录，以便不单独记忆密码。
- 作为管理员，我希望预先维护手机号和岗位，以便员工不能自行选择岗位。

**验收标准**：

- [ ] 已在职且手机号匹配的员工可以完成绑定并获取登录令牌。
- [ ] 未匹配、已停用或重复手机号返回待绑定/不可登录状态。
- [ ] 岗位从服务端员工档案取得，前端传入岗位参数不生效。
- [ ] 每个已绑定 OpenID 只能对应一个有效员工。

**输入**：微信登录凭证、微信手机号凭证。

**输出**：登录令牌、角色、员工信息、唯一岗位或 `pending_binding` 状态。

**业务规则**：普通员工不允许自行注册、改岗位或绑定他人手机号；管理员绑定和岗位变更必须写入审计日志。

#### 3.2.2 人员与岗位管理

**功能描述**：管理员维护六类固定岗位及每类岗位的一名在岗员工。

**用户故事**：

- 作为管理员，我希望维护姓名、工号、手机号、岗位和在职状态，以便系统正确分配任务。
- 作为普通员工，我希望在“我的”页面看到自己的岗位，便于确认职责范围。

**验收标准**：

- [ ] 只能使用后勤、保安、保健、保育、厨房、业务人员六类岗位。
- [ ] 员工只能关联一个岗位。
- [ ] 每个岗位当前最多一名在岗员工，超过时阻止保存并提示管理员。
- [ ] 停用员工不再接收未来任务，但历史记录保留。

**输入**：员工姓名、工号、手机号、岗位、账号角色、在职状态。

**输出**：员工列表、员工详情、绑定状态和岗位信息。

**业务规则**：只有管理员能创建、修改和停用员工档案。

#### 3.2.3 Excel 细则导入与审核

**功能描述**：管理员上传业务部门及后勤细则 Excel，系统确定性解析工作表和行，生成任务模板草稿与知识切片草稿，管理员核对后分别发布。

**用户故事**：

- 作为管理员，我希望上传原始细则并看到来源行，以便逐条审核而不丢失依据。
- 作为管理员，我希望未确认的草稿不参与任务和问答，以便避免错误发布。

**验收标准**：

- [ ] 仅管理员可上传 Excel。
- [ ] 系统保留原文件、文件哈希、工作表名和行号。
- [ ] 无法确定岗位、周期、时间规则或任务内容的行标记为待补全。
- [ ] 未审核草稿不能生成任务，也不能被 RAG 检索。
- [ ] 模板发布和知识发布可以独立执行。

**输入**：`.xlsx` 文件。

**输出**：文档记录、解析状态、任务模板草稿、知识切片草稿和解析错误。

**业务规则**：Excel 解析器不使用大模型补全缺失规则；管理员是唯一发布者。

#### 3.2.4 确定性周期任务生成

**功能描述**：基于已审核启用的模板、园历规则和在岗员工生成任务实例。

**用户故事**：

- 作为普通员工，我希望打开小程序就看到当天应办任务。
- 作为管理员，我希望任务生成可重复执行且不会重复建单。

**验收标准**：

- [ ] 后勤、保健、保育、厨房、业务人员只在周一至周五工作日生成任务。
- [ ] 周末、法定节假日、寒暑假不生成普通岗位任务。
- [ ] 保安当前一人时，已启用保安任务直接分配给该保安；周末规则按模板执行。
- [ ] 模板缺字段、日期冲突或没有在岗员工时不生成任务，并记录异常。
- [ ] 同一模板、员工和应办日期重复运行只保留一条任务。
- [ ] LangGraph 和大模型没有任务写入权限。

**输入**：目标日期、已启用模板、园历、在岗员工。

**输出**：任务实例、生成原因或异常记录。

**业务规则**：任务引擎使用确定性 Python 规则，不根据自然语言或模型回答临时创建任务。

#### 3.2.5 员工任务提交与修改申请

**功能描述**：员工查看本人任务并提交完成状态、完成时间、备注和最多三张现场照片。已提交任务只能通过申请更改重新开放。

**用户故事**：

- 作为普通员工，我希望提交现场照片和备注，以便留下完成证据。
- 作为普通员工，我希望发现提交错误时申请更改，而不是直接覆盖历史。
- 作为管理员，我希望审核修改原因，以便保留任务过程记录。

**验收标准**：

- [ ] 员工只能提交自己的待完成任务。
- [ ] 每次提交保存独立版本，历史版本不可覆盖。
- [ ] 已提交任务只能发起更改申请并填写原因。
- [ ] 管理员同意后任务回到待完成，员工必须重新提交。
- [ ] 管理员拒绝必须填写原因，原提交保持已提交。

**输入**：任务 ID、备注、最多三张照片或修改申请原因。

**输出**：提交版本、任务状态、审核结果和拒绝原因。

**业务规则**：

```text
待完成 -> 已提交 -> 更改待审核
更改待审核 -> 管理员同意 -> 待完成
更改待审核 -> 管理员拒绝 -> 已提交
```

#### 3.2.6 岗位职责 RAG 与对话

**功能描述**：员工询问本岗位职责、今日/本周任务和工作要求，LangGraph 只检索当前岗位已发布知识切片并返回来源。

**用户故事**：

- 作为普通员工，我希望询问“今天有哪些保健任务”，以便快速了解工作要求。
- 作为管理员，我希望每条回答可追溯到 Excel 的文档、工作表和行号。

**验收标准**：

- [ ] 普通员工检索条件由服务端强制设置为本人岗位和 `published` 状态。
- [ ] 前端不能通过参数切换岗位或读取其他岗位知识。
- [ ] 有效回答必须返回本次实际检索到的来源切片。
- [ ] 无充分依据时固定回复：`当前已审核工作细则未包含此要求，请联系管理员确认。`
- [ ] LangGraph 不拥有任务、员工、模板、园历或知识发布写工具。
- [ ] 普通员工不能上传或修改 RAG 文档。

**输入**：当前登录身份、问题文本。

**输出**：回答、来源文档/工作表/行号、拒答标记或固定拒答。

**业务规则**：只回答已发布知识中的内容，不提供外部搜索、常识补充、推测性安全建议或无来源答案。

#### 3.2.7 小程序界面

**员工端底部导航**：`今日`、`任务`、`问答`、`我的`。

**管理员端底部导航**：`概览`、`任务`、`知识库`、`管理`。

前端根据服务端角色显示对应导航，但所有接口仍由后端鉴权。员工端重点展示今日待办和提交操作，管理员端重点展示待审核事项、模板、知识库和园历。

## 4. 非功能需求

### 4.1 性能需求

| 指标 | 要求 |
|------|------|
| 普通查询响应时间 | 在开发测试环境中，常规任务和员工信息查询目标为 2 秒内返回；具体生产指标待部署阶段确定 |
| 对话响应时间 | 允许受模型调用影响；接口需支持超时、重试和明确失败提示 |
| 并发用户数 | MVP 面向单园内部使用，首版不承诺集团级并发容量 |
| 数据量 | 以六类岗位、单园员工和 Excel 细则为初始规模；表结构支持后续扩展 |

### 4.2 安全需求

- [x] 微信登录凭证由后端交换，小程序不保存服务端密钥。
- [x] 所有受保护接口进行令牌鉴权。
- [x] 后端强制管理员/普通员工角色权限。
- [x] 普通员工查询自动追加本人或岗位过滤。
- [x] 上传、发布、绑定、审核和状态变更写入审计日志。
- [x] 照片、手机号、微信凭证不写入普通应用日志。
- [x] RAG 检索必须限制为当前岗位已发布切片。

### 4.3 可用性需求

- 员工从登录到今日任务不超过三步。
- 任务卡显示状态、时间段、截止时间和工作要求。
- 上传、解析、审核失败时显示可读原因，不显示无意义的内部堆栈。
- 没有 RAG 依据时使用固定拒答，不以不确定内容误导员工。

### 4.4 兼容性需求

- 前端使用微信原生小程序能力，适配常见微信移动端环境。
- 后端 API 使用 JSON；照片上传使用受控文件接口。
- Excel MVP 只支持 `.xlsx`，其他格式明确拒绝。

### 4.5 可维护性需求

- 前端按 View、Controller、Model/Service 分层。
- 后端按 API、Service、Repository、Model、Schema 分层。
- 任务生成、状态机和 RAG 引用校验必须有独立单元测试。
- 任务实例保存模板版本和岗位快照；知识回答保存文档版本和引用切片。

## 5. 数据需求

### 5.1 数据实体

| 实体 | 描述 | 关键属性 |
|------|------|----------|
| 岗位 | 六类固定职责分类 | `code`、`name` |
| 员工 | 管理员或岗位员工 | 姓名、工号、手机号、OpenID、岗位、在职状态、角色 |
| 园历 | 任务生成所依据的日期规则 | 日期、工作日类型、原因 |
| 任务模板 | 经管理员审核启用的周期工作规则 | 岗位、周期、时间段、截止规则、内容、验收要点、版本 |
| 任务实例 | 针对某员工某日期的应办任务 | 模板、员工、岗位快照、应办日期、状态 |
| 任务提交 | 员工每次提交的不可覆盖版本 | 提交时间、备注、照片、版本号 |
| 修改申请 | 员工要求重新提交的申请及管理员处理结果 | 原因、状态、处理人、处理原因 |
| 知识文档 | 管理员上传的原始 Excel 及版本 | 文件名、哈希、上传人、解析/审核状态 |
| 知识切片 | 带岗位授权和来源定位的 RAG 文本 | 岗位、周期、任务标签、工作表、行号、向量、发布状态 |
| 对话记录 | 员工问题、回答和引用 | 员工、会话、问题、回答、引用切片 |
| 审计日志 | 关键操作追踪 | 操作者、动作、资源、时间、结果 |

### 5.2 数据流

```text
管理员员工档案 -> 微信手机号匹配 -> OpenID 绑定 -> 角色/岗位上下文

Excel -> 原文件保存 -> 确定性解析 -> 任务模板草稿 + 知识切片草稿
     -> 管理员审核发布 -> 任务规则引擎 / pgvector RAG

已启用模板 + 园历 + 在岗员工 -> 任务实例
任务实例 -> 员工提交版本 -> 修改申请 -> 管理员审核 -> 新提交版本

员工问题 + 服务端岗位上下文 -> LangGraph -> 岗位过滤检索
     -> 有来源回答 / 固定拒答
```

### 5.3 数据存储

| 数据类型 | 存储方式 | 保留策略 |
|----------|----------|----------|
| 员工、岗位、园历、任务和审核 | PostgreSQL | 业务记录和历史状态长期保留 |
| RAG 原始 Excel | 文件存储，数据库保存文件哈希和元数据 | 保留版本，发布记录不可覆盖 |
| RAG 知识切片和向量 | PostgreSQL + pgvector | 按文档版本保留；停用后不可检索 |
| 任务照片 | 受控文件存储，数据库保存对象键 | 由管理员后续配置保留周期 |
| 审计日志 | PostgreSQL 追加式表 | 不允许普通用户修改或删除 |

## 6. 接口需求

### 6.1 外部接口

| 接口名称 | 类型 | 提供方 | 用途 |
|----------|------|--------|------|
| 微信登录接口 | REST | 微信开放平台 | 获取登录身份和手机号授权结果 |
| 小程序业务接口 | REST/JSON | FastAPI | 认证、员工、任务、园历、审核和对话 |
| 小程序文件上传接口 | REST/Multipart | FastAPI | 上传 Excel 和任务照片 |
| 大模型接口 | REST/SDK | 配置的模型服务商 | 仅用于已检索上下文的回答生成 |

### 6.2 内部接口

```text
POST /auth/wechat/login
GET  /me

GET  /tasks/today
GET  /tasks/{task_id}
POST /tasks/{task_id}/submissions
POST /tasks/{task_id}/change-requests

GET  /admin/staff
POST /admin/staff
PATCH /admin/staff/{staff_id}
GET  /admin/task-templates
POST /admin/task-templates
PATCH /admin/task-templates/{template_id}

POST /admin/change-requests/{request_id}/approve
POST /admin/change-requests/{request_id}/reject
```

所有受保护接口从服务端令牌获取当前用户，不接受前端的 `staff_id` 或 `position_id` 作为授权依据。Repository 层必须追加普通员工的数据范围条件。

## 7. 约束条件

### 7.1 技术约束

- 前端必须使用微信原生小程序界面。
- 后端必须使用 FastAPI，并按 MVC/分层方式组织。
- 数据库采用 PostgreSQL + pgvector。
- 对话编排采用 LangGraph，但智能体没有任何业务写权限。
- 任务状态机和任务生成使用确定性 Python 代码。

### 7.2 业务约束

- 首版只支持管理员和普通员工。
- 首版只支持后勤、保安、保健、保育、厨房、业务人员六类岗位。
- 每个岗位当前只有一名在岗员工，保安周末规则由模板确定；未来多人时再扩展排班。
- 后勤、保健、保育、厨房、业务人员按周一至周五工作日生成；周末、节假日和寒暑假不生成。
- 只有管理员可上传、审核和发布 RAG 文档。
- Excel 草稿未经管理员审核不得参与任务生成或问答。
- 无已发布依据时必须固定拒答，不能让模型自行补充。

### 7.3 资源约束

- MVP 先完成代码与本地开发链路，不在本阶段确定正式部署方式。
- 初始数据来自两份幼儿园业务/后勤工作细则 Excel。
- 正式微信小程序配置、域名、对象存储和生产级定时任务另行设计。

## 8. 风险分析

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|----------|
| Excel 行内容缺少明确岗位或周期 | 任务无法安全自动生成 | 高 | 解析为待审核草稿，管理员补全后才能发布 |
| 模型生成无依据内容 | 可能导致错误执行或安全风险 | 中 | 强制岗位过滤、来源引用校验和固定拒答 |
| 前端伪造岗位或员工 ID | 越权访问其他岗位数据 | 中 | 服务端从令牌读取身份，Repository 强制数据范围过滤 |
| 园历、调休或寒暑假配置错误 | 生成错误任务 | 中 | 管理员维护园历，规则冲突时不生成并记录异常 |
| 员工提交后直接覆盖记录 | 无法追溯任务过程 | 低 | 追加式提交版本和修改申请状态机 |
| 保安人数增加后分配不明确 | 周末任务可能重复或漏派 | 低 | 当前固定单人，预留排班表，扩展前先启用管理员排班 |
| 微信手机号授权失败 | 员工无法绑定 | 中 | 提供待绑定状态和管理员手工处理入口 |
| 文件或照片存储策略未确定 | 数据保留和成本不可控 | 中 | MVP 只抽象文件存储接口，部署阶段确定具体策略 |

## 9. 验收标准

### 9.1 功能验收

- [ ] 管理员可以维护六类岗位和每岗位一名在岗员工。
- [ ] 微信手机号匹配后能绑定 OpenID；未匹配账号不能访问业务数据。
- [ ] 普通员工只能查看本人任务和本岗位已发布知识。
- [ ] 管理员可上传 Excel，系统生成带工作表和行号来源的草稿。
- [ ] 未发布模板不生成任务，未发布知识不参与 RAG。
- [ ] 工作日、节假日、寒暑假和保安周末规则生成结果符合配置。
- [ ] 任务生成重复执行不重复创建任务。
- [ ] 员工提交支持备注、完成时间和最多三张照片。
- [ ] 员工只能申请修改，管理员同意后重新开放，拒绝必须有原因。
- [ ] RAG 回答必须有实际来源；无依据时返回固定拒答。
- [ ] LangGraph 无任务和知识库写入权限。
- [ ] 关键操作有审计日志。

### 9.2 性能验收

- [ ] 常规任务和员工信息查询在开发测试环境目标为 2 秒内返回。
- [ ] 对话接口具备超时和失败提示，不因模型服务异常改变业务数据。
- [ ] 大文件上传和解析有进度/状态反馈，解析失败可定位原因。

### 9.3 文档验收

- [ ] 本文档完成业务、用户、功能、非功能、数据、接口、约束和风险章节。
- [ ] API、状态机、权限矩阵和 RAG 过滤规则与实现保持一致。
- [ ] 两份初始 Excel 作为参考文档登记，并保留导入后的来源定位。
