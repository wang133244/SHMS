# 幼儿园人员与岗位职责 MVP 开发设计

设计日期：2026-10-21

## 1. 目标与范围

本 MVP 是面向单个幼儿园内部员工的微信原生小程序。它把岗位人员、周期任务和经过审核的岗位工作细则连接为一个闭环：员工查看并提交任务，管理员审核异常；员工通过对话查询本岗位已发布的职责细则。

首版固定管理六类岗位：后勤、保安、保健、保育、厨房、业务人员。每类岗位当前仅设置一名在岗员工。首版只有管理员和普通员工两种账号角色。

### 1.1 MVP 成功标准

1. 管理员能预置六类岗位的员工资料，并通过员工微信手机号完成首次绑定。
2. 管理员能上传 Excel 细则，将内容解析成待审核的任务模板草稿和岗位知识草稿。
3. 仅已审核并启用的任务模板按确定性规则生成应办任务。
4. 员工能提交任务、提交修改申请，并查看管理员的审核结果。
5. 员工只能访问本人任务和本岗位已发布知识；管理员能跨岗位管理。
6. 对话仅依据当前岗位的已发布知识回答，并能返回来源。无检索依据时拒绝回答，不补充模型常识。

### 1.2 明确不在范围内

- 家长、幼儿、招生、资产、推广、研修等其他业务模块。
- 多园区、多租户、集团管理和部署方案。
- 多岗位、兼岗和多人轮班。保安轮班数据结构预留，但当前不启用。
- 绩效评分、审批流、自动奖惩和 AI 自动创建或修改任务。
- 员工上传知识、PDF/Word/图片知识导入，以及通用闲聊。

## 2. 已确认业务规则

### 2.1 账号与岗位

- 管理员预先维护员工的姓名、工号、手机号、岗位和在职状态。
- 员工首次进入小程序时完成微信登录并授权手机号。后端以手机号匹配员工档案，匹配成功后绑定微信 OpenID。
- 未匹配用户处于待绑定状态，不能读取任务、知识库或对话接口。
- 每位普通员工只属于一个岗位。岗位不可由员工自行选择或通过前端参数修改。
- 管理员可管理全部岗位、员工、模板、任务、园历、知识文档和审核记录。

### 2.2 园历与任务生成

- 后勤、保健、保育、厨房、业务人员的任务只在园历标记为工作日的周一至周五生成。
- 周末、法定节假日、寒暑假不生成上述岗位的任务。管理员维护例外日期和调休。
- 当前保安仅一人。保安模板可按全日或周末规则生成，直接分配给该保安；未来多人时再启用轮班。
- 每条任务模板明确岗位、周期、执行日期规则、时段、截止规则、工作内容、验收要点、生效范围和启用状态。
- 系统只使用已审核、已启用且规则完整的模板生成任务。规则缺失、冲突或没有匹配在岗员工时，不生成任务，并产生管理员可见异常。
- 同一模板、员工、应办日期组合只能存在一条任务实例，保证生成操作可重复执行而不重复建单。

### 2.3 任务提交与修改

任务状态机如下：

```text
待完成
  -> 员工提交 -> 已提交
                    -> 员工申请更改 -> 更改待审核
                                           -> 管理员同意 -> 待完成
                                           -> 管理员拒绝 -> 已提交
```

- 提交记录包括提交时间、备注和最多三张现场照片。
- 员工不能直接修改或撤回已提交任务，只能提交修改申请并填写原因。
- 管理员同意后保留原提交记录，将任务重新开放为待完成；员工须创建新的提交版本。
- 管理员拒绝时必须填写原因，任务保持已提交，员工可查看原因后再次申请。
- 所有提交、申请、审核和状态变化保留不可覆盖的历史记录和审计日志。

## 3. 总体架构

```text
微信原生小程序
  员工端 / 管理员端页面
          |
          v
FastAPI
  认证鉴权 / 业务 API / Excel 导入 / 对话 API / 任务规则服务
          |
          +--------------------+
          |                    |
          v                    v
PostgreSQL + pgvector       LangGraph
业务数据、审计、知识切片     受限检索与有来源回答编排
```

### 3.1 技术选型

| 层级 | 选型 | 原因 |
|---|---|---|
| 小程序 | 微信原生小程序，WXML、WXSS、JavaScript/TypeScript | 与微信登录、手机号授权和相机上传直接集成。 |
| 后端 | FastAPI | 适合结构化 API、Pydantic 校验和异步文件/模型调用。 |
| 关系与向量数据 | PostgreSQL + pgvector | 在同一事务边界内处理任务、权限元数据、审计与向量检索。 |
| 智能体编排 | LangGraph | 把认证上下文、受限检索、来源校验和回答节点显式拆开。 |
| Excel 解析 | Python Excel 解析库 | 将结构化单元格转换为可审核草稿；不使用大模型推断任务规则。 |

大模型供应商通过服务端适配器配置，API 密钥不进入小程序、代码仓库或数据库业务表。

### 3.2 MVC 组织方式

小程序使用页面 View、页面 Controller 和 API/状态 Model 分层；FastAPI 使用路由 Controller、业务 Service、数据库 Repository/Model 分层。权限校验位于 FastAPI 依赖层和 Service 层，不能只放在小程序页面判断。

建议目录：

```text
miniapp/
  pages/                 # View: 员工与管理员页面
  controllers/           # 页面事件、表单校验、页面状态协调
  services/              # HTTP 请求、登录、上传
  models/                # 当前用户、任务、知识等前端模型
  components/
  utils/

backend/
  app/api/               # FastAPI 路由 Controller
  app/services/          # 认证、任务、导入、知识、对话业务规则
  app/repositories/      # 数据访问与强制数据范围过滤
  app/models/            # SQLAlchemy ORM 模型
  app/schemas/           # Pydantic 输入输出模型
  app/agents/            # LangGraph 图、检索工具、输出校验
  app/jobs/              # 可重复调用的任务生成服务
  tests/
```

## 4. 小程序界面与交互

员工和管理员共用一个小程序，根据服务端返回的账号角色显示入口。前端隐藏入口只改善体验，不能代替接口鉴权。

### 4.1 员工端

底部导航为：`今日`、`任务`、`问答`、`我的`。

| 页面 | 主要内容与操作 |
|---|---|
| 今日 | 日期、今日应办数量、待完成/即将到期任务卡、岗位问答入口。 |
| 任务 | 按待完成、已提交、更改待审核筛选本人任务；进入详情。 |
| 任务详情 | 显示来源模板、时段、工作要求、截止时间、提交历史；提交备注和照片，或申请更改。 |
| 问答 | 仅面向本人岗位的职责、今日/本周任务和工作要求；每条答复显示来源。 |
| 我的 | 姓名、工号、岗位、绑定状态和退出登录。 |

### 4.2 管理员端

底部导航为：`概览`、`任务`、`知识库`、`管理`。

| 页面 | 主要内容与操作 |
|---|---|
| 概览 | 在岗员工数、今日任务数、逾期数、待审核修改申请、待审核 RAG 草稿和未绑定用户。 |
| 任务 | 模板草稿/启用管理、按岗位查看任务实例、查看提交版本、审核修改申请。 |
| 知识库 | 上传 Excel、查看解析状态、审核/发布/停用知识切片、按岗位和来源追溯。 |
| 管理 | 员工预置与绑定、岗位查看、园历例外、保安规则、审计日志。 |

## 5. 数据模型

### 5.1 核心表

| 表 | 关键字段 | 说明 |
|---|---|---|
| `positions` | `id`、`code`、`name` | 固定六类岗位字典。 |
| `staff` | `id`、`name`、`employee_no`、`phone`、`openid`、`position_id`、`account_role`、`employment_status` | 一名员工只能关联一个岗位；管理员也使用此表。 |
| `work_calendars` | `date`、`day_type`、`reason` | 工作日、周末、节假日、寒暑假和调休。 |
| `task_templates` | `id`、`position_id`、`frequency`、`schedule_rule`、`time_range`、`due_rule`、`content`、`acceptance_criteria`、`status`、`version`、`source_document_id`、`source_row` | 已审核并启用才可生成。 |
| `security_schedules` | `date`、`staff_id`、`duty_type` | 为未来多名保安轮班预留；当前可由唯一保安默认匹配。 |
| `task_instances` | `id`、`template_id`、`template_version`、`staff_id`、`position_id_snapshot`、`due_date`、`due_at`、`status`、`generation_reason` | 对模板、员工和应办日期加唯一约束。 |
| `task_submissions` | `id`、`task_instance_id`、`version`、`submitted_at`、`note`、`photo_keys` | 追加式保存，不更新历史版本。 |
| `change_requests` | `id`、`task_instance_id`、`requester_id`、`reason`、`status`、`reviewer_id`、`review_note`、`reviewed_at` | 拒绝时 `review_note` 必填。 |
| `knowledge_documents` | `id`、`file_name`、`file_hash`、`uploaded_by`、`version`、`parse_status`、`review_status` | 仅管理员可创建。 |
| `knowledge_chunks` | `id`、`document_id`、`position_id`、`frequency`、`task_label`、`source_sheet`、`source_row`、`content`、`embedding`、`publish_status` | RAG 检索的最小授权单位。 |
| `chat_sessions` / `chat_messages` | 会话、员工、问题、回复、引用切片 ID | 用于对话历史和审计。 |
| `audit_logs` | 操作者、动作、资源类型、资源 ID、前后摘要、时间 | 保存关键管理和审核行为。 |

### 5.2 数据一致性约束

- `positions.code` 唯一，只允许六个已定义值。
- `staff.employee_no`、`staff.phone` 唯一；`openid` 绑定后唯一。
- 普通员工的 `position_id` 非空，且不可存在多个现任岗位关联。
- `task_instances(template_id, staff_id, due_date)` 唯一。
- `task_submissions(task_instance_id, version)` 唯一，并禁止修改已存在版本。
- `knowledge_chunks` 必须携带 `position_id` 和来源定位；发布状态不是 `published` 的切片不可检索。

## 6. 认证、授权与接口范围

### 6.1 微信登录与绑定

1. 小程序调用 `wx.login` 获取临时登录凭证，并通过微信手机号授权获取手机号凭证。
2. FastAPI 在服务端完成微信凭证交换，取得 OpenID 与手机号。
3. 后端以手机号匹配预置且在职的 `staff` 记录，成功后写入 OpenID 并签发访问令牌。
4. 未匹配则返回 `pending_binding`，前端只能展示待绑定说明。
5. 每个受保护接口从令牌获取当前员工，不接受前端传入的 `staff_id`、`position_id` 作为授权依据。

### 6.2 两类权限

| 资源 | 管理员 | 普通员工 |
|---|---|---|
| 员工与岗位 | 全部查看、维护、绑定 | 查看本人资料。 |
| 任务模板与园历 | 创建、审核、启用、停用、维护 | 不可访问。 |
| 任务实例 | 查看全部、处理例外、审核修改申请 | 仅查看和提交本人任务。 |
| RAG 文档与知识 | 上传、解析、审核、发布、停用 | 只能检索本人岗位已发布内容。 |
| 对话 | 跨岗位管理查询可作为后续管理功能 | 仅本岗位问答。 |

Repository 层必须在所有普通员工查询中追加 `staff_id = current_user.id` 或 `position_id = current_user.position_id`。即使用户伪造请求参数，也不能跨岗位读取记录。

### 6.3 关键 API

```text
POST /auth/wechat/login
GET  /me

GET  /tasks/today
GET  /tasks/{task_id}
POST /tasks/{task_id}/submissions
POST /tasks/{task_id}/change-requests

GET  /admin/staff
POST /admin/staff
PATCH /admin/staff/{staff_id}
GET  /admin/task-templates
POST /admin/task-templates
PATCH /admin/task-templates/{template_id}
POST /admin/task-templates/{template_id}/publish
POST /admin/change-requests/{request_id}/approve
POST /admin/change-requests/{request_id}/reject
PATCH /admin/calendar/{date}

POST /admin/knowledge-documents/import-excel
GET  /admin/knowledge-documents/{document_id}/drafts
POST /admin/knowledge-chunks/{chunk_id}/publish
POST /chat/ask
```

所有写接口要求令牌、角色校验、Pydantic 参数校验和审计日志。上传接口还要验证文件类型、大小、哈希和上传者身份。

## 7. Excel 导入与任务模板审核

管理员是唯一允许上传 RAG 源文件的角色。初始数据使用已有业务人员细则与后勤各部门工作细则作为参考来源。

### 7.1 导入流程

```text
管理员上传 Excel
  -> 保存原文件与哈希
  -> 确定性解析工作表和行
  -> 生成任务模板草稿与知识切片草稿
  -> 管理员逐条核对、补全岗位/周期/规则
  -> 管理员分别发布模板和知识切片
```

解析器只处理明确的列值，例如周期、时间、任务职责和工作细则。无法识别岗位、周期、时间规则或来源行时，草稿标为 `needs_review`，不可自动发布。解析器不得让大模型推断缺失的周期、分配对象或截止时间。

每一个草稿保留源文件版本、工作表名、行号和原始文本。模板发布与知识发布可独立进行，以免未确认的任务规则进入任务引擎。

## 8. 确定性任务引擎

任务引擎实现为可测试的 `generate_tasks_for_date(target_date)` 服务，而不是由 LangGraph 或大模型执行。开发阶段通过命令或受保护管理接口触发；部署阶段再由可靠的外部计划任务按中国时区调用。

生成步骤：

1. 读取目标日期的园历类型和所有已启用模板。
2. 根据岗位和模板日期规则判断是否应执行。普通岗位仅允许工作日；保安依据其明确的全日、工作日或周末规则。
3. 查询该岗位唯一在岗员工。当前保安为唯一在岗保安时直接匹配。
4. 计算时间段和截止时间，校验字段完整性。
5. 使用数据库唯一约束插入任务实例；已存在则跳过。
6. 对规则冲突、缺员或无效日期写入异常日志，供管理员处理。

任务引擎不会根据问答内容、模型输出、员工提交内容或自然语言临时创建任务。

## 9. 严格 RAG 与 LangGraph 设计

### 9.1 固定图结构

```text
认证后的当前用户
  -> 问题范围校验
  -> 服务端写入岗位过滤条件
  -> pgvector 检索已发布知识切片
  -> 检索充分性判断
       -> 不充分：固定拒答
       -> 充分：受限上下文回答
  -> 引用校验与响应返回
```

LangGraph 只编排以上只读步骤。它没有任务、模板、员工、园历、知识发布或数据库写入工具。

### 9.2 检索与回答约束

- 检索过滤条件由后端根据令牌写入：普通员工固定为 `position_id = current_user.position_id AND publish_status = 'published'`。
- 前端传来的岗位筛选参数被忽略。管理员的跨岗位检索需显式管理权限并记录审计日志。
- 回答上下文仅包含检索到的原文、文档版本、工作表名和行号。
- 模型输出使用结构化响应：`answer`、`citations`、`refusal`。`citations` 必须是本次实际检索到的切片 ID。
- 后端验证所有引用均属于本次检索结果且至少包含一个来源。不满足时不返回模型正文，改为固定拒答。
- 没有足够已发布依据时固定回复：`当前已审核工作细则未包含此要求，请联系管理员确认。`
- 不提供一般常识、外部搜索、推测性建议或无来源的安全/保健/保育要求。

## 10. 错误处理与审计

- 未绑定、令牌失效、越权访问、任务状态非法跳转和已撤销模板等情况返回明确的机器错误码与用户可读信息。
- Excel 解析失败保存失败原因，不写入可发布知识或任务模板。
- 文件上传、任务提交照片和微信凭证不得记录到普通应用日志。
- 管理员的员工绑定、岗位变更、园历变更、模板发布、知识发布、修改申请审核均写入 `audit_logs`。
- 任务实例保存模板版本和岗位快照；知识回答保存引用切片与文档版本，保证历史可追溯。

## 11. 测试与验收

### 11.1 后端单元与集成测试

1. 微信手机号成功匹配、未匹配和已停用员工三种登录结果。
2. 普通员工不能以伪造的任务 ID、员工 ID 或岗位 ID 读取跨岗位数据。
3. 管理员可访问全部数据，普通员工仅能操作本人任务。
4. 工作日、节假日、寒暑假、调休和保安周末模板的任务生成结果。
5. 对同一模板、员工、日期重复运行生成服务时只生成一条任务。
6. 模板规则缺失、员工不在岗、日期冲突时不生成任务并创建异常记录。
7. 任务提交、修改申请、同意、拒绝与再次提交的全部状态转换；拒绝缺少理由必须失败。
8. Excel 解析产生草稿，未发布模板和知识切片不得参与任务生成或 RAG。
9. RAG 检索必须自动附加岗位和发布状态过滤；无来源、跨岗位引用或未检索引用的回答必须被拒绝。

### 11.2 小程序验收

1. 员工端仅显示今日、任务、问答、我的四个入口，并正确显示本人任务状态。
2. 管理员端显示概览、任务、知识库、管理入口及待处理数量。
3. 任务提交支持备注和最多三张照片；已提交任务只能发起更改申请。
4. 管理员审核同意后员工可重新提交；拒绝原因在员工端可见。
5. 每条有效问答显示可点击或可展开的文档、工作表和行号来源。

## 12. 后续实现边界
